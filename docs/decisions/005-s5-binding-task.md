# 005 S5：游戏账号绑定与代练任务

日期：2026-10-29　状态：已实现并验证（gofmt / vet / build / 全量 go test 192 包通过；user + admin vue-tsc 通过；真实二进制 + SQLite 冒烟通过）

## 范围（用户 2026-10-29 选定）

- S5 做：用户侧绑定 / 解绑 / 验证码 / 游戏内确认、下单冻结、取消；服务端执行状态机和结算（领取、进度、要输入、完成、失败、确认取消、超时回收）。
- 留给 S6：签名认证、Worker 节点、租约（token、90 秒、`LEASE_LOST`）、`request_id` 去重、按能力 pull、租约过期回收。S6 在 `TaskService` 的执行端函数外面加这些，**不另写一份状态机**。
- 另加**开发用模拟执行端**：配置 `boost.dev_simulator`（默认 `false`），后台"代练管理 → 代练任务 → 模拟执行端"手动推进绑定 / 任务。S6 上线后删除。

## 决定

1. **凭据加密。** `infrastructure/credential`：AES-256-GCM（复用 `internal/crypto`），密钥来自新配置 `boost.credential_keys`（版本 → 密钥，≥ 32 字符，不能和 `app.secret_key` 相同，否则拒绝启动）。密文带版本前缀 `v1:…`，轮换时加新版本并改 `credential_key_version`，旧密文照常解密。没配密钥时服务正常启动，只是不能绑定账号。凭据、会话、验证码同一套加密。
2. **登录名。** 只存掩码（规则同原型 `maskLogin`）和指纹 `sha256(game_id:小写登录名)`。同一用户同一游戏同一登录名只能有一个有效绑定（S1 的部分唯一索引兜底）。每人每天（北京时间）最多 10 次绑定。
3. **验证码。** 提交时加密存进 `boost_inputs`，执行端领取时解密下发，然后立即清空密文、标记 consumed。等待 5 分钟，超时由回收置失败（任务 `INPUT_TIMEOUT` 全额退，绑定 FAIL）。
4. **解绑。** 有未结束任务拒绝（`BINDING_BUSY`）；否则凭据、会话置空，软删除。之后可以重新绑定同一账号。
5. **并发上限按功能计。** `max_active_per_user` 按规范（boost-feature-schema.md §2）是"该功能"的进行中任务数。原型实现按用户全部任务数，和规范不一致；Go 以规范为准。检查前先锁用户积分账户，让同一用户的下单串行。
6. **快照。** 任务保存 `feature_version`、`snapshot_json`（名称、能力、退款策略、时限、上限、折扣率）、`plan_json`（步骤、固定费、单位数、合计、明细，键名同原型）、规范化后的 `params_json`（前端多传的字段，包括任何价格字段，都被 Compile 丢掉）。结算只读快照。
7. **结算。** `consumedFor` 同原型：成功 / 取消按完成量（`featuredef.PointsForUnits`）；失败时 `none` 全扣，`full_on_system_fail` 遇系统错误码全退，其余按完成量。完成量只增不减、超过计划截断。终态和积分结算同一事务，积分侧 `consume:task:{id}` / `release:task:{id}` 保证只结算一次，状态机再拒绝重复完成。
8. **错误码表。** `domain/errorcode.go` 是服务端权威表（同原型）；执行端上报的 `retryable` 只对表里没有的码生效。可重试且未超次数、未过时限 → 回 PENDING（退避 30s × 2^(n-1)）。`LOGIN_FAILED` / `ACCOUNT_BANNED` / `PASSWORD_CHANGED` 同时让绑定 FAIL；排队中的任务领取时发现绑定已失效，直接失败全退。
9. **同一绑定只跑一个任务。** 领取时检查，`idx_boost_tasks_processing_binding` 部分唯一索引兜底（测试直接写库验证被拒）。
10. **脱敏。** 事件、进度文字写库前去掉该绑定的登录名 / 密码原文和 `password: xxx` / `验证码=xxx` 形式，截断 500 字。列表接口不带任何密文；模拟执行端回显不含凭据和验证码。
11. **回收。** 复用 S4 的每分钟维护任务 `boost:points_maintain`：处理过期输入和超过 `deadline_at` 的任务（`FAIL(TIMEOUT)`，按完成量）。
12. **权限。** `operations` 角色：任务、绑定、模拟执行端；`support` 角色：查看任务 / 绑定、取消任务。取消和模拟操作写入审计。
13. **页面。** 用户端：`/boost/accounts`（添加 / 验证码 / 游戏内确认 / 解绑），`/boost/:code` 选账号下单（内联确认，幂等键每次打开确认生成），`/boost/tasks` 和 `/boost/tasks/:taskNo`（进度条、步骤、执行记录、验证码、取消；进行中每 5 秒刷新）。后台："代练管理 → 代练任务"（任务 / 游戏账号 / 模拟执行端三个标签）。

## 补充（2026-10-29）：按步骤上报完成量

用户验收时发现：执行端只报总完成数时，服务端只能假设"按步骤顺序执行"，如果执行端先刷了贵的 BOSS 关，扣的钱就和实际不符。用户选定方案 B：

1. 执行端在心跳 / 完成 / 失败 / 确认取消时上报 `steps: [{seq, done}]`，可以只报有变化的步骤；不存在或重复的 seq 拒绝。每一步只增不减，超过计划数截断。完成时不带 `steps` 表示全部完成。
2. 任务新增 `steps_done_json`（例如 `[8,10]`），`units_done` = 各步之和（只用于进度显示）。结算用 `featuredef.PointsForSteps`：Σ 每一步完成数 × 单价 + 固定部分（开始执行后才收），打折向下取整，不超过冻结；全部完成 = 合计。
3. 旧任务（新列为 NULL）按步骤顺序从 `units_done` 推导，结果和 S5 初版一致（测试覆盖）。
4. 领取时下发 `steps_done`，重试的执行端据此跳过已完成的部分。
5. 任务详情新增"结算明细"（用户端和后台都有）：每一步 完成 / 计划 × 单价 = 小计、固定部分、折扣、冻结 / 扣除 / 退回和本次用的规则（例如"失败（体力不足）：按每一步已完成次数 × 单价扣除，其余退回"）。进行中显示为预估。
6. 模拟执行端改为逐步填写完成数。
7. 与原型的差异：原型 `pointsForUnits` 按顺序累加；Go 以用户选定的方案 B 为准，`PointsForUnits` 保留只给 golden 对照测试用。

## 验证

- `internal/modules/boost/integrationtest/task_test.go` 22 个场景，对应 engine.test.js 的任务 / 绑定用例（定义从原型 seed 导出到 `testdata/seed_defs.json`，预期积分用原型算出）；每个场景后检查不变量：积分三处相等、冻结 = 未结束任务冻结之和、已结束任务 消耗 + 退回 = 冻结、同一绑定最多一个执行中任务。另有 150 步随机操作。
- `task_http_test.go`：返回体不泄露密码 / 密文 / 指纹、别人的任务和绑定看不到改不了、前端价格无效、模拟端默认关闭、审计。
- 冒烟：真实二进制 + 新 SQLite，HTTP 走通 登录 → 建游戏 / 功能 → 发积分 → 绑定 → 模拟验证 → 下单（幂等重复返回原任务）→ 进度 4 → 体力不足失败 → 消耗 10 退回 4 → 解绑销毁凭据。日志和数据库文件里都找不到密码原文，0 个 500。
