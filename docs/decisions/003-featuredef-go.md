# 003 S2：功能定义引擎的 Go 实现

日期：2026-10-26　状态：已实现并验证

## 决定

1. **位置。** `internal/modules/boost/domain/featuredef`，只依赖标准库。对外提供 `Validate` / `ValidateJSON`、`Normalize`、`Compile`、`PointsForUnits`、`StepProgress`、`ApplyRate`。后台保存、预览、用户报价、服务端下单都只调用这里，没有第二份实现。
2. **按 JavaScript 语义逐条移植。** 原型是规则的权威来源，Go 版连 JS 的类型转换都照搬：`Number(" 60 ")` 是 60，`"0x10"` 是 16；字符串长度按 UTF-16 码元计，一个 emoji 算 2 个字；对象键顺序和 `JSON.parse` 一致；`undefined` 和 `null` 分开处理。为此单独写了 `Value` 类型，没有用 `map[string]any`，因为后者会丢键顺序，也分不出"缺失"和 `null`。
3. **对照测试代替手写断言。** `prototype/tools/gen-featuredef-golden.js` 用原型算出期望结果，写入 `testdata/golden.json`。目前有 316 条校验用例和 402 条编译用例，覆盖：
   - 6 个示例定义，以及 `catalog.test.js` 的全部场景；
   - 每个长度、数值上限的"刚好合法"和"刚好超出"；
   - 随机改坏定义（240 条），随机生成参数（360 条，混有边界值和垃圾值）；
   - 每个编译用例在 0 … units+1 各完成量下的结算积分和步骤进度。

   Go 测试要求输出的 JSON 和原型**逐字节一致**。原型规则一改，就要重新生成 golden 并一起提交。
4. **前端报价走服务端。** 用户端和后台预览都调用服务端接口拿 `Compile` 结果，浏览器里不再算一遍。理由是单一实现、以后不会出现两边不一致，代价是每次修改参数都要发一次请求。Compile 是纯计算，单次在毫秒以内。
5. **已知差异：`text.pattern` 按 Go RE2 语法解释**，不支持反向引用和环视。管理员写了这类正则时，保存会提示"不是合法的正则表达式"，所以不会出现"能保存、下单时却校验不一致"的情况。

## 顺带修复的原型问题

随机变异测试发现原型 `validateDefinition` 遇到某些非法目录会抛异常，没有返回校验错误，比如分组不是对象、`items` 是字符串。已修（`catalog.js` 检查 `cost_by` 的两处），原有 47 个原型测试仍全部通过。Go 版本来就不会出这个问题。

## 验证

- `go test ./internal/modules/boost/...`：golden 全部一致；
- 变异检查：把折扣改成四舍五入，70 条用例失败；去掉关卡去重，27 条失败；把每个长度上限各放宽 1，每处都至少有 1 条失败。只有两处改动没有用例失败，是结算里"全部完成 = 总价"和"不超过总价"这两道保护：折扣函数是单调的（已穷举验证），这两行不会改变结果，留着只是防御；
- `internal/architecture` 分层测试通过。
