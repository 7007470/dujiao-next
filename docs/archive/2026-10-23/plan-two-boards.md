# Dujiao-Next 两大板块开发计划

> 用于新的独立仓库。先开发、先测试，暂不迁移旧用户、订单、余额或账号。

## 1. 目标和边界

### 板块一：根据角色选择的账号交易

用户选择游戏、区服、角色和账号属性，筛选符合条件的账号，购买指定账号，完成支付、交付、绑定和售后。

### 板块二：自动代练

用户选择代练商品，保存自己的游戏账号，完成必要绑定，支付后创建代练任务，由 Worker 执行并回传进度和结果。

Dujiao-Next 直接复用用户、会员等级、会员折扣、钱包、商品、订单、支付、退款、权限和通用后台。第一版不做批发、积分、分销、自动续费、自动计划、人工打手派单和多商城。

## 2. 架构

```text
Dujiao-Next：用户 / 会员 / 钱包 / 商品 / 订单 / 支付 / 退款 / 权限
                         │
                         ▼
游戏扩展：账号交易 + 自动代练 + 必要绑定和 Worker 接口
                         │
                         ▼
游戏 Worker（独立进程，不直连商城数据库）
```

先作为 Dujiao-Next 自定义模块开发，不一开始拆多个新服务。只有部署或故障隔离确实需要时才拆服务。

## 3. 阶段总览

| 阶段 | 交付物 | 难度 | 进入条件 |
|---|---|---:|---|
| S0 | 固定版本、测试实例和决策记录 | 低 | 无 |
| S1 | 两个模块骨架和扩展接入 | 中 | S0 |
| S2 | 游戏、角色、账号和筛选 | 中 | S1 |
| S3 | 指定账号预留、支付、交付和售后 | 高 | S2 |
| S4 | 代练商品、绑定账号和已支付权益 | 中高 | S1、S3 可并行 |
| S5 | Worker 任务、租约、进度和结果 | 最高 | S4 |
| S6 | 最小用户端、管理端和审计 | 中 | S2–S5 |
| S7 | 并发、幂等、安全、重启和全链路验收 | 高 | S6 |
| S8 | 真实数据迁移设计（不执行） | 高 | S7 冻结通过 |

每一阶段都必须有测试结果和决策记录，不能因页面完成跳过库存、支付或租约测试。

## 4. S0：固定版本和测试环境

### 任务

- 新建独立 Git 仓库；
- 记录 upstream、release、commit、Go、前端、数据库和 Redis 版本；
- 建立 `docs/decisions/`、`docs/api/`、`docs/test-results/`；
- 使用独立测试数据库、对象存储、邮件、支付、测试用户、测试账号和测试 Worker；
- 确认当前版本的模块注册、订单支付事件和数据库迁移入口；
- 验证登录、创建商品、创建订单、模拟支付和关闭订单。

### 验收

```text
[ ] 固定 commit 能启动
[ ] 管理员和测试用户可以登录
[ ] 测试订单可创建、支付模拟、关闭
[ ] 重复支付回调不会重复处理
[ ] 测试环境没有旧库连接串
[ ] docs/decisions/000-version.md 已记录事实
```

难度低；源码和文档不一致时暂停并固定实际可运行版本。

## 5. S1：两个业务模块骨架

建议目录（以当前 Dujiao 架构为准，名称不可盲目照抄）：

```text
internal/modules/gameaccount/   # 板块一
internal/modules/boost/         # 板块二
internal/modules/workerapi/     # Worker 运输层
internal/workflows/game/        # 账号交付流程
internal/workflows/boost/       # 代练任务流程
```

### 任务

- 增加最小模块、迁移和测试；
- 增加依赖检查；
- 定义错误码、幂等键、审计字段和状态转换函数；
- 定义 Dujiao 订单与自定义业务的关联；
- 找到支付成功的真实接入点；
- 不复制会员、钱包和订单代码。

### 验收

自定义模块编译、加载、迁移重复执行和架构测试通过；游戏模块不能直接写钱包；Worker 模块不能直连商城数据库。

## 6. S2：板块一——游戏账号和角色筛选

### 最小模型

```text
game
game_server
game_attribute_definition
game_account
game_account_attribute
game_account_credential
```

账号属性必须可索引。角色、等级、武器、皮肤等筛选数据由属性定义和值表达；公开 JSON 只用于展示摘要。

`game_account` 至少有游戏、区服、外部账号 ID、标题、公开属性、价格、凭据引用、销售状态和版本号。

### 第一版规则

- 只做指定账号购买，不做批发数量和批量拿货；
- 多个角色条件先固定为 AND；同一角色数量使用 `>=`；
- 游戏和属性删除改为隐藏，有引用时禁止物理删除；
- 列表和详情不返回密码、绑定参数和外部连接配置。

### 验收

角色筛选结果准确；多条件有测试；下架账号不展示；价格由服务端计算；无权限用户看不到敏感数据。

难度中，主要风险是属性模型和后续库存状态保护。

## 7. S3：板块一——指定账号交易

### 流程

```text
提交 account_id
→ 服务端重新报价
→ 原子预留 ON_SALE → LOCKED
→ 创建 Dujiao 订单和商品快照
→ 支付成功
→ LOCKED → SOLD
→ 写交付引用
→ 已购订单查看凭据
```

### 必做

- 预留使用数据库条件更新或行锁；
- 预留失败和订单失败整体回滚；
- 支付失败、取消、超时释放预留；
- 支付回调幂等；
- 快照保存账号标题、区服、角色属性和价格；
- 退款和换号有权限和审计；
- 指定账号不自动替换成其他账号。

### 自动化验收

1. 100 个并发请求购买同一账号，只有一个成功。
2. 支付回调重复 10 次，只产生一次交付。
3. 订单超时或支付失败后账号可再次销售。
4. 账号资料后续修改不改变历史快照。
5. 同步不会重新上架 `LOCKED` 或 `SOLD` 账号。

这是板块一的核心高风险阶段，应优先于复杂页面。

## 8. S4：板块二——代练商品、绑定账号和权益

### 最小模型

```text
boost_plan
boost_plan_parameter
boost_user_binding
boost_entitlement
```

代练商品包含游戏、功能编码、名称、价格、参数定义、有效期或可执行次数、状态和说明。第一版优先做“按次权益”，不做积分和自动续费。

### 流程

```text
创建代练商品
→ 用户购买
→ Dujiao 支付成功
→ 幂等创建 boost_entitlement
→ 用户选择绑定账号和功能
→ 原子消耗一次权益
→ 创建 PENDING 任务
```

### 规则和验收

- 支付成功只创建一份权益；
- 下架商品不影响已购权益；
- 过期或用完不能创建任务；
- 并发创建不会超出权益次数；
- 绑定凭据加密，验证码短期有效；
- 用户只能看到自己的绑定和权益；
- 退款和权益撤销可重复执行。

难度中高，重点是订单幂等和权益并发消费。

## 9. S5：板块二——Worker 任务

### 逻辑接口

```text
POST /worker/auth
POST /worker/tasks/pull
POST /worker/tasks/{id}/heartbeat
POST /worker/tasks/{id}/progress
POST /worker/tasks/{id}/finish
POST /worker/tasks/{id}/fail
POST /worker/tasks/{id}/cancel
```

真实 URL、认证和扩展位置必须以固定版本源码为准。

### 任务模型

```text
boost_task
  user_id, entitlement_id, binding_id, game_id, feature_code
  parameters_json, status, idempotency_key
  worker_id, lease_token, lease_expires_at
  progress_percent, progress_text, result_json
  error_code, attempt, deadline_at, created_at, updated_at

boost_task_event
  task_id, sequence, event_type, message, data_json, created_at
  UNIQUE(task_id, sequence)
```

### 租约规则

- pull 原子更新 `PENDING`；
- 写入 Worker ID、随机 Token、过期时间和尝试次数；
- 只有当前 Token 能心跳、上报、结束；
- 过期任务回到 `PENDING` 或 `FAIL`；
- 旧 Token 返回 `LEASE_LOST`；
- 所有结束回调带 request ID；
- Worker 不直连 Dujiao 数据库。

### 验收

两个 Worker 并发领取只能一个成功；重复完成不重复消耗权益；Worker 崩溃后可恢复或最终失败；旧租约不能覆盖新结果；取消状态能传达给 Worker；用户能查看进度和结果。

这是全计划最高风险阶段。

## 10. S6：最小页面和权限

### 用户端

游戏列表、角色筛选账号列表、账号详情购买、已购账号凭据、代练商品、我的绑定账号、创建代练任务、任务进度、输入提示和结果。订单、会员、钱包页面复用 Dujiao 原生页面。

### 管理端

游戏和角色属性、账号库存和上下架、账号同步/导入、账号售后、代练商品、绑定和代练任务、Worker 节点、订单退款和审计。

优先使用 Dujiao 原生 Vue，禁止无产品原因再维护一套 React 用户端。

## 11. S7：全链路验收和迁移冻结

必须验证：

1. 测试用户注册、会员折扣和钱包支付；
2. 角色筛选准确；
3. 并发购买不重复售出；
4. 重复支付不重复交付；
5. 订单超时释放账号；
6. 同步不覆盖锁定/已售账号；
7. 代练支付只创建一份权益；
8. Worker 领取、心跳、进度、完成；
9. Worker 失联后恢复或失败结算；
10. `WAIT_INPUT` 可以恢复；
11. 失败、取消和退款符合记录规则；
12. 权限、脱敏、审计通过；
13. 重启后订单、账号、权益和任务状态正确。

### 冻结条件

连续三次全链路测试、自动化测试、并发幂等测试、备份恢复和回滚演练全部通过；版本固定；敏感数据审计通过；剩余风险已列出；新旧系统的钱包、订单和账号责任边界已确定。满足前不得迁移真实数据。

## 12. S8：真实数据迁移（只定义入口，不执行）

另开迁移方案，顺序建议：

```text
用户 → 会员等级 → 钱包余额和流水 → 游戏/角色 → 游戏账号和加密凭据 → 商品 → 已完成订单 → 未完成订单和任务
```

禁止直接复制旧表、用昵称匹配、跳过钱包流水，或让两个系统同时扣款。
