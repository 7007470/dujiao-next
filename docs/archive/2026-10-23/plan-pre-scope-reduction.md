# Dujiao-Next 游戏账号与自动代练二次开发计划

> 本计划用于一个新的独立仓库。不要在原 FYPLAY 仓库中执行本计划，也不要在真实数据上开发。

**目标：** 基于固定版本的 Dujiao-Next，先完成游戏账号、会员、钱包、自动代练和绑定功能的独立测试闭环，确认功能和稳定性后再制定真实数据迁移方案。

**总体架构：** Dujiao-Next 继续负责用户、会员、钱包、商品、订单、支付和通用后台。游戏账号、角色筛选、库存同步、绑定任务、代练套餐和 Worker 任务作为自定义游戏模块，通过 Dujiao-Next 的官方扩展点、工作流、事件和模块接口连接。游戏 Worker 通过任务接口访问自定义游戏模块，不直接访问商城数据库。

**技术前提：** Go、Vue 3、Dujiao-Next 官方扩展方式、PostgreSQL 或经过验证的数据库方案、Redis（生产异步任务需要时）、现有游戏 Worker 协议或新的 HTTPS 任务协议。

**前置规则：** 先阅读根目录 `AGENTS.md`。本计划只描述开发，不包含真实数据迁移。每项任务必须独立验证后才能进入下一项。

| 阶段 | 目标 | 难度 | 依赖 | 结果 |
|---|---|---:|---|---|

| 2 | 游戏、角色、账号和后台管理 | 中 | 1 | 能录入和查询测试账号 |
| 3 | 账号预留、售出确认和交付 | 高 | 2 | 一个账号不会重复销售 |
| 4 | 外部库存同步 | 高 | 3 | 同步不覆盖锁定/已售账号 |
| 5 | 会员、钱包和订单适配 | 中高 | 1、3 | 会员折扣和支付闭环稳定 |
| 6 | 代练套餐和订阅权益 | 中高 | 5 | 支付后能产生有效权益 |
| 7 | Worker 任务协议和执行闭环 | 最高 | 6 | Worker 能租约、执行、回报、重试 |

## 二、阶段 0：独立仓库和测试环境

### 目标

建立一个与当前 FYPLAY 完全隔离的新 Git 仓库，固定 Dujiao-Next 版本，能在本地或测试服务器启动用户端、管理端、数据库和 Redis。

### 必做事项

- 创建独立 Git 仓库。
- 记录 Dujiao-Next upstream URL、版本号和 commit。
- 复制根目录 `AGENTS.md`。
- 建立 `docs/decisions/`、`docs/api/`、`docs/test-results/`、`scripts/`。
- 使用测试域名、测试邮件、测试支付配置和测试 Worker。
- 禁止使用旧 FYPLAY 数据库连接串。
- 建立最小备份和恢复脚本。

### 验收

```text
[ ] 全新环境可以按 README 启动
[ ] 管理员可以登录管理端
[ ] 测试用户可以注册和登录
[ ] 测试数据库为空且与旧库无连接
[ ] Redis、日志和上传目录均为测试目录
[ ] 版本和 commit 已写入 docs/decisions/000-version.md
```

### 失败处理

如果官方 README、当前代码和部署文档不一致，暂停开发，记录差异，固定可运行的 release 或 commit，不直接追踪开发分支。

## 三、阶段 1：自定义模块骨架

### 目标

建立一个不修改 Dujiao-Next 核心源码的游戏扩展骨架，并让它能被编译、启动和迁移。

### 建议模块

```text
gamecatalog       游戏和角色目录
gameaccount       游戏账号与库存
gamefulfillment   账号交付
gamebind          绑定任务
boost             代练套餐、权益和任务
workerapi         Worker 认证与任务接口
```

如果 Dujiao-Next 的实际扩展机制不支持以上目录，必须以当前版本的官方方式为准，不能为了匹配计划强行创建伪模块。

### 必做事项

- 定义模块接口，不先写业务实现。
- 定义表名前缀和 ID 规则。
- 定义状态常量和状态迁移函数。
- 定义错误码、幂等键和审计字段。
- 增加一个最小测试实体和测试迁移，验证扩展加载。
- 增加架构测试，阻止游戏模块直接访问钱包内部实现。

### 验收

- 全部模块可编译。
- 数据库迁移可重复执行。
- 应用启动时自定义模块加载成功。
- 自定义模块测试失败不会污染 Dujiao-Next 核心数据。

## 四、阶段 2：游戏、角色、账号和查询

### 目标

先不接外部库存，只使用测试数据实现游戏账号的录入、筛选和脱敏展示。

### 最小数据模型

```text
game
game_role_category
game_role
game_account
game_account_role
```

`game_account` 至少需要：游戏 ID、区服、平台、外部账号 ID、展示字段、凭据引用、价格、库存状态、来源 ID、版本号、创建/更新时间。

`game_account_role` 负责可索引的角色编码和数量，不把所有筛选字段永久塞进不可查询的 JSON。

### 状态

```text
ON_SALE
LOCKED
SOLD
OFF_SALE
SYNC_ERROR
```

### 必做事项

- 管理员维护游戏、角色分类和角色。
- 管理员录入测试账号和角色属性。
- 用户按游戏、区服、角色、价格和状态查询。
- 公共列表只返回脱敏字段。
- 购买前展示的字段和订单快照字段分开定义。
- 凭据只保存加密引用，不在列表接口返回。

### 验收

- 角色数量筛选结果正确。
- 无权限用户看不到账号密码、绑定参数和源连接配置。
- 价格由服务端返回，前端不能篡改。
- 下线账号不出现在可售列表。

## 五、阶段 3：账号预留、订单和交付

### 目标

把指定账号的销售做成原子、幂等和可恢复的流程。

### 状态流程

```text
ON_SALE
  └─ reserve → LOCKED
LOCKED
  ├─ payment success → SOLD
  ├─ payment failure → ON_SALE
  ├─ order timeout → ON_SALE
  └─ cancel → ON_SALE
```

### 必做事项

- 创建订单和账号预留必须有唯一约束。
- 支付回调必须使用幂等键。
- 同一账号并发购买必须只有一个成功。
- 订单超时任务必须释放账号。
- 支付成功后生成不可变商品快照。
- 交付记录与订单项绑定，不能仅靠商品 ID 查询当前库存。
- 退款前检查账号是否已经绑定、使用或交付。

### 验收

必须自动化验证：

1. 100 个并发请求购买同一账号，只有一个成功。
2. 支付回调重复 10 次，余额和订单只变化一次。
3. 支付失败后账号可以再次购买。
4. 订单超时后账号可以再次购买。
5. 已售账号不会重新出现在列表。
6. 订单快照不随账号后续编辑变化。

## 六、阶段 4：外部库存同步

### 目标

接入一个测试外部库存源，完成可预演、差异同步、失败记录和状态保护。

### 同步原则

- 先全量读取和规范化，再计算差异。
- 先预演，再写入。
- 通过稳定外部 ID 去重，不通过账号昵称匹配。
- 每次同步保存来源、开始时间、结束时间、耗时、计数和错误。
- `LOCKED`、`SOLD`、绑定中账号不能被普通同步改回 `ON_SALE`。
- 外部源删除记录不等于立即删除本地已售记录。

### 验收

- 新增、变更、下线、跳过和错误数量正确。
- 重复执行同一快照不会产生重复账号。
- 同步中断后可以重试。
- 并发手动同步和定时同步不会同时写同一来源。
- 测试覆盖外部字段为空、重复 ID、异常连接和部分失败。

## 七、阶段 5：会员、钱包和订单适配

### 目标

只复用 Dujiao-Next 已有能力，不复制一套会员或钱包。

### 必做事项

- 确认会员等级、等级折扣和商品价格的真实接口。
- 定义游戏商品和代练套餐如何参与会员价计算。
- 定义余额支付、充值、退款的唯一来源。
- 定义订单付款成功事件和重复事件处理。
- 保存购买时的会员等级、折扣和价格快照。
- 明确代练失败时的退款或权益恢复规则。

### 禁止事项

- 不创建第二个钱包。
- 不直接修改钱包余额表。
- 不从前端传入最终支付金额。
- 不用普通商品订单号代替代练任务幂等号。

### 验收

- 不同会员等级的价格正确。
- 钱包余额不足时订单和账号状态可恢复。
- 重复支付回调不重复扣款。
- 退款不重复入账。
- 历史订单不会随会员等级变化而改变。

## 八、阶段 6：代练套餐和订阅权益

### 目标

实现“套餐是商品，权益是支付后的可消费资源，任务是权益的一次使用”这三个概念的分离。

### 最小数据模型

```text
boost_plan
boost_plan_feature
boost_subscription
boost_quota_ledger
```

套餐至少需要：游戏、名称、价格、有效期、功能编码、次数或时长、状态、排序和说明。

订阅至少需要：会员、游戏账号、套餐、订单、开始时间、过期时间、剩余次数/时长和状态。

### 验收

- 支付成功只创建一次权益。
- 过期权益不能创建任务。
- 次数型权益并发消费不会变成负数。
- 任务失败是否返还次数必须有明确规则和测试。
- 删除或下架套餐不影响已有订单和权益。

## 九、阶段 7：Worker 任务协议

### 目标

让现有或新的游戏 Worker 可以安全执行代练任务。

### 接口

```text
POST /worker/auth
POST /worker/tasks/pull
POST /worker/tasks/{id}/heartbeat
POST /worker/tasks/{id}/progress
POST /worker/tasks/{id}/finish
POST /worker/tasks/{id}/fail
POST /worker/tasks/{id}/cancel
```

真实路径以 Dujiao-Next 当前扩展方式为准，以上是逻辑接口，不得未经验证直接当成最终 URL。

### 任务状态

```text
PENDING
PROCESSING
WAIT_INPUT
SUCCESS
FAIL
CANCELLED
```

### 租约规则

- pull 只能原子领取 PENDING 任务。
- 领取时写入 worker ID、租约 Token 和过期时间。
- 只有当前有效租约可以写入心跳、进度和结果。
- 租约过期后任务可以重新领取。
- 旧 Worker 的迟到请求必须被拒绝。
- 完成和失败接口必须以任务 ID、租约 Token 和幂等请求号校验。

### 验收

- 两个 Worker 并发领取同一任务只有一个成功。
- 旧租约不能覆盖新租约结果。
- 重复完成请求结果一致。
- Worker 崩溃后任务能在租约过期后恢复。
- 管理员取消任务后 Worker 收到取消状态。
- 进度日志可分页查看且不泄露凭据。

## 十、阶段 8：账号绑定

### 目标

把已有绑定思想迁移为独立的绑定任务流程，不与代练任务混用状态。

### 绑定流程

```text
创建绑定任务
→ PENDING
→ Worker PROCESSING
→ WAIT_INPUT
→ 用户提交输入
→ PENDING
→ PROCESSING
→ SUCCESS / FAIL
```

### 必做事项

- 每个绑定任务绑定订单项、账号和游戏。
- Worker 只能领取匹配游戏和协议的任务。
- 输入数据分类型保存，验证码设置有效期。
- 任务结果和用户提示分开保存。
- 绑定成功后锁定账号售后规则。
- 绑定超时、重试和用户放弃有明确行为。

### 验收

- `WAIT_INPUT` 用户提交后可以恢复任务。
- 不匹配协议的 Worker 无法领取。
- 旧租约无法完成新任务。
- 绑定失败不会泄露账号密码。
- 重试次数和最终失败状态符合规则。

## 十一、阶段 9：前台和后台产品化

### 前台

- 游戏列表和游戏详情；
- 账号筛选；
- 账号详情和购买；
- 代练游戏、套餐和权益；
- 代练任务控制台；
- 订单、钱包、会员等级；
- 绑定输入和任务状态。

### 后台

- 游戏和角色；
- 账号及库存来源；
- 同步预演和同步日志；
- 代练套餐和功能；
- Worker 管理；
- 绑定任务和代练任务；
- 订单、退款和审计。

### 规则

- 优先使用 Dujiao-Next 原生 Vue 管理端和用户端。
- 不同时维护一套 React 用户端，除非有明确产品原因。
- 页面展示状态必须来自服务端。
- 页面隐藏不能代替后端权限和 DTO 隔离。

## 十二、阶段 10：全链路验收和迁移冻结

### 必须通过的业务场景

1. 新用户注册、登录和充值。
2. 会员等级折扣正确。
3. 指定账号筛选和购买。
4. 并发购买不会重复售出。
5. 支付重复回调不会重复扣款。
6. 订单超时释放账号。
7. 账号库存同步不覆盖锁定和已售状态。
8. 代练套餐支付后只创建一次权益。
9. Worker 任务领取、心跳、进度和完成。
10. Worker 失联后任务恢复。
11. 用户输入验证码后绑定继续。
12. 代练失败、绑定失败和退款处理正确。
13. 管理员权限、用户隔离和凭据脱敏正确。
14. 重启 Dujiao-Next 后订单、权益、任务和租约状态正确恢复。

### 冻结条件

只有以下条件全部满足，才能开始设计真实数据迁移：

- 连续三次完整测试通过；
- 自动化测试通过；
- 并发测试通过；
- 数据库备份和恢复演练通过；
- 任务和支付幂等测试通过；
- 敏感数据审计通过；
- 许可证和对外分发方式已记录；
- 版本已固定；
- 回滚方案已经在测试环境执行过；
- 所有未完成事项已列出并明确不影响迁移。

## 十三、阶段 11：真实数据迁移设计（本计划不执行）

### 迁移顺序

```text
用户
→ 会员等级
→ 钱包余额和流水
→ 游戏和角色目录
→ 游戏账号
→ 商品和套餐
→ 已完成订单
→ 未完成订单和任务
```

### 必须准备

- 旧 ID 到新 ID 的映射表；
- 用户、余额、流水、订单和账号数量核对；
- 账号凭据加密转换方案；
- 未完成订单和绑定任务处理方案；
- 重复执行保护；
- 分批迁移和暂停点；
- 回滚和只读恢复方案。

### 禁止做法

- 直接复制旧数据库表到新数据库；
- 用昵称、邮箱或账号名作为唯一映射；
- 把旧钱包余额直接写入新钱包而不写流水；
- 迁移期间同时让两个系统扣款；
- 在没有核对快照的情况下删除旧数据。

## 十四、每阶段固定交付物

每个阶段结束必须有：

1. 代码和数据库迁移；
2. 接口文档；
3. 正常和异常测试；
4. 验证命令及输出摘要；
5. 操作说明；
6. 已知风险；
7. `docs/decisions/` 决策记录；
8. 本计划的勾选状态更新。

## 十五、AI 执行格式

后续 AI 每次执行任务必须按下面格式开始和结束：

### 开始

```text
阶段：
任务：
已读文件：
当前事实：
本次修改：
明确不修改：
成功标准：
不确定点：
```

### 结束

```text
已完成：
修改文件：
测试命令：
测试结果：
未完成：
风险：
下一步：
```

如果 AI 无法填写其中任意一项，必须先停止并补充信息，不得继续猜测实现。
