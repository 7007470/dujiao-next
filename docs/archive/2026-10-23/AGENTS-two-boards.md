# Dujiao-Next 二次开发规则

本仓库只做两个自定义业务板块：

1. **角色筛选账号交易**：按游戏、区服、角色和账号属性筛选，购买指定账号，安全交付和售后。
2. **自动代练**：购买代练商品，绑定用户游戏账号，创建任务，由 Worker 执行并回传进度和结果。

Dujiao-Next 已有的用户、会员等级、会员折扣、钱包、商品、订单、支付、退款、权限和审计是基础能力，不算第三个业务板块。除非当前版本没有对应能力，否则禁止重新实现。

## 1. 严格范围

### 必须开发

- 游戏、区服、角色目录和可索引账号属性；
- 指定账号的筛选、原子预留、支付确认、交付和售后；
- 代练商品、已支付权益、用户游戏账号绑定和代练任务；
- Worker 认证、租约、心跳、进度、完成、失败和取消；
- 完成两个板块所需的最小用户端和管理端页面。

### 暂不开发

用户明确要求前禁止加入：批发、积分或点数、第二钱包、分销代理、多级返利、自动续费、每日自动计划、人工打手派单、多商城、多租户、与游戏无关的营销功能和“未来可能需要”的抽象层。

代练第一版是“购买代练商品并创建任务”，不是积分平台。代练价格由 Dujiao-Next 商品和订单处理。

## 2. 固定架构

```text
Dujiao-Next：用户 / 会员 / 钱包 / 商品 / 订单 / 支付 / 退款 / 权限
                         │
自定义游戏业务：账号交易 + 自动代练 + 必要的绑定和 Worker 接口
                         │
游戏 Worker：独立进程，不直连商城数据库
```

- 游戏模块不得直接修改钱包余额、订单金额或支付记录。
- Worker 不得直连商城数据库。
- 前端不得自行判断支付、库存、会员、绑定或任务最终状态。
- 不复制一套会员、钱包或订单系统。
- 不把需要角色筛选的游戏账号粗暴当成普通卡密。

## 3. 核心不变量

### 3.1 账号交易

- 账号公开属性必须可查询；密码、绑定参数和外部源凭据不得进入列表接口。
- 同一账号同时只能有一个有效预留。
- 创建订单不等于支付成功；支付失败、超时、取消必须释放预留。
- 已锁定、已售出或绑定中的账号不得被同步重新标为可售。
- 支付成功后保存不可变商品快照，交付必须关联具体订单项。
- 售后、换号和退款必须幂等并写审计。
- 并发购买同一账号只能一个成功。

账号状态只能是：

```text
DRAFT → ON_SALE → LOCKED → SOLD → REVOKED
          └──────→ OFF_SALE
LOCKED → ON_SALE
```

### 3.2 自动代练

- 任务必须关联已支付权益和一个绑定账号。
- 权益不能被并发重复消费。
- 同一绑定账号默认只能有一个执行中的任务。
- 一个任务同一时刻只能由一个有效 Worker 持有租约。
- 没有有效租约的 Worker 不能写进度、成功或失败。
- 完成、失败、取消和回调必须幂等。
- Worker 只能上报执行事实，不能决定退款金额。
- 凭据和验证码不得写进普通日志。

任务状态只能是：

```text
PENDING → PROCESSING → SUCCESS
              ├──────→ FAIL
              ├──────→ WAIT_INPUT → PENDING
              └──────→ CANCELLED
```

租约过期后只能回到 `PENDING` 或进入 `FAIL`，由重试次数决定；旧租约迟到请求必须拒绝。

## 4. 版本、数据和许可证

- 固定 Dujiao-Next release 或 commit，禁止直接跟踪 `main`/`develop`。
- 记录 Go、前端、数据库和 Redis 版本。
- 开发使用独立数据库、对象存储、Redis、支付配置、测试用户和测试 Worker。
- 迁移冻结前禁止连接或修改生产数据；禁止导入真实余额、订单和账号密码。
- 自定义表使用 `game_`、`boost_`、`worker_` 前缀。
- 钱、数量、时长、折扣使用整数或定点类型，禁止浮点金额。
- 凭据加密保存并记录密钥版本，日志只允许脱敏值。
- 不改 Dujiao 原表，除非官方扩展点确实无法满足需求，并记录迁移和回滚。
- Dujiao-Next 使用 GPL-3.0。保留版权和许可证；对外分发前单独检查 GPL 义务。

## 5. AI 防失忆规则

每次开始工作前按顺序读取：

1. `AGENTS.md`；
2. `docs/dujiao-next-customization-plan.md`；
3. `docs/game-business-design.md`（如果存在）；
4. `docs/decisions/` 中有关记录；
5. 当前任务源码、接口、测试和 Git 状态。

每次开始先报告：

```text
阶段和任务：
已完成前置条件：
当前已确认事实：
本次修改文件：
明确不修改文件：
验收标准：
不确定点及验证方式：
```

无法确认版本、扩展方式、接口、状态或数据结构时，必须先查源码或运行实例；不得根据旧文档、页面名称或接口名称猜测。事实与计划冲突时停止编码并报告。

## 6. 精准修改和验证

- 只改当前任务需要的文件，不顺手重构无关代码。
- 不为暂不开发的业务预留代码。
- 只有存在两个真实实现或明确替换点时才增加接口。
- 状态机、库存预留、支付、退款、租约和幂等必须先有可失败测试或可重复验证。
- 编译通过、页面打开、Mock 成功都不能单独证明业务完成。
- 测试必须覆盖正常、并发、重复、超时、失败、取消、权限、脱敏和重启恢复。

每次结束更新计划并报告：

```text
已完成：
修改文件：
测试命令和结果：
未完成：
风险：
下一步唯一建议：
```

## 7. 完成定义

一个阶段只有同时满足以下条件才算完成：代码、迁移和接口文档已提交；正常、并发、幂等、失败、权限和脱敏验证通过；迁移可重复；重启后状态正确；计划和决策记录已更新；剩余风险已列出。真实数据迁移不属于开发完成条件，必须另开任务。
