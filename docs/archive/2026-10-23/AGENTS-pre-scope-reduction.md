# Dujiao-Next 游戏业务二次开发规则

## 1. 项目目标

本项目基于 Dujiao-Next 二次开发，目标是完成以下业务：

1. 游戏账号展示、角色筛选、指定账号购买和安全交付。
2. 会员注册、会员等级、折扣、钱包、充值和退款。
3. 自动代练套餐、订阅权益、代练任务、Worker 执行、进度和结果。
4. 游戏账号绑定，包括租约、验证码输入、等待用户输入、成功、失败和重试。
5. 在真实数据迁移前，使用独立测试数据完成完整闭环验证。

最终成功标准不是“页面能打开”，而是下面的业务链路可以重复、幂等、可恢复：

```text
用户注册
→ 选择游戏账号或代练套餐
→ 创建订单
→ 支付成功
→ 账号或权益被唯一锁定
→ 创建绑定/代练任务
→ Worker 领取并执行
→ 回传进度和结果
→ 用户看到交付结果
→ 失败、取消、超时、退款均有明确处理
```

## 2. 不可改变的架构方向

### 2.1 Dujiao-Next 的职责

Dujiao-Next 原有模块优先负责：

- 用户身份和登录；
- 会员等级和会员价；
- 钱包、充值、余额流水；
- 商品、订单、支付和退款基础流程；
- 通用后台、权限和系统配置。

### 2.2 自定义游戏模块的职责

新增游戏模块负责：

- 游戏、区服、角色、账号和账号属性；
- 外部账号库存同步；
- 游戏账号的原子预留、释放和售出确认；
- 账号凭据的安全存储与交付；
- 账号绑定任务和绑定协议；
- 代练套餐、订阅权益和游戏任务；
- Worker 领取、租约、心跳、进度、完成、失败和取消。

游戏模块不得直接修改 Dujiao-Next 的钱包余额、订单最终金额或支付记录。必须通过稳定的模块接口、工作流、事件或官方扩展点协作。

### 2.3 Worker 的职责

游戏 Worker 是独立执行程序，不属于商城后台队列。Worker 只通过任务接口访问游戏任务，不直接访问商城数据库。

Worker 必须支持：

- 身份认证；
- 任务租约；
- 租约过期保护；
- 心跳；
- 幂等的进度和结果上报；
- 取消检查；
- 可重试错误与不可重试错误区分。

## 3. 开发前必须确认的事实

任何 AI 开始修改代码前，必须先回答并记录：

1. 当前使用的 Dujiao-Next 版本、Git commit、Go 版本和前端版本是什么？
2. 当前仓库是否是官方 fork？自定义代码放在哪里？
3. 使用 SQLite 还是 PostgreSQL？生产是否启用 Redis？
4. Dujiao-Next 当前版本的订单、支付、会员和钱包接口实际名称是什么？
5. 当前 Worker 是否已有可调用协议？协议文档、状态值和认证方式是什么？
6. 本任务需要改动哪些文件？哪些文件明确不应修改？
7. 本任务的输入、输出、状态变化和失败处理是什么？
8. 能否写出一个可以失败的测试或可重复的验证步骤？

如果上述事实无法确认，必须先检查源码、官方文档或运行实例。不得凭项目名称、旧版本文档、页面类型或接口名称推断功能已经存在。

## 4. 长期防失忆规则

### 4.1 每次开始工作先读这些文件

每个新的 AI 会话或自动续接，必须按顺序阅读：

1. 根目录 `AGENTS.md`；
2. `docs/dujiao-next-customization-plan.md`；
3. `docs/decisions/` 中与当前任务有关的决策记录；
4. 当前任务涉及模块的 README、接口和测试；
5. Git 状态、当前分支和最近提交。

不得因为“上一次已经知道”而跳过。上下文可能已经丢失，文件才是项目事实来源。

### 4.2 每次开始工作先写状态摘要

开始修改前，在回复中明确写出：

- 当前阶段和任务编号；
- 已完成的前置条件；
- 本次要修改的文件；
- 不会修改的文件；
- 验收标准；
- 当前不确定点和处理方式。

### 4.3 每次结束工作更新进度

结束前必须更新开发计划中的状态：

- 已完成事项；
- 验证命令及结果；
- 未完成事项；
- 新发现的风险；
- 下一步唯一建议。

禁止只说“基本完成”“应该可以”“测试没问题”，必须给出证据。

## 5. 数据和环境隔离规则

### 5.1 开发期禁止真实迁移

在所有阶段达到迁移冻结条件前，禁止：

- 修改生产数据库；
- 连接真实会员钱包；
- 导入真实用户余额；
- 导入真实订单；
- 批量导入真实账号密码；
- 使用真实支付回调做测试；
- 让测试 Worker 执行真实用户任务。

开发必须使用独立的：

- Git 仓库或分支；
- Dujiao-Next 测试实例；
- 测试数据库；
- 测试对象存储；
- 测试 Redis；
- 测试支付配置；
- 测试 Worker 和测试游戏账号。

### 5.2 版本固定

必须固定 Dujiao-Next 的 release 或 commit。禁止直接在 `main`、`develop` 或未记录 commit 的工作树上开发。

每次升级必须先记录：

- 原版本和目标版本；
- 数据库迁移变化；
- 自定义扩展的编译和测试结果；
- 回滚方式。

### 5.3 数据库规则

- 自定义表使用独立且有前缀的命名空间，例如 `game_`、`boost_`、`worker_`。
- 不修改 Dujiao-Next 原表结构，除非官方扩展点无法满足需求，并且已经记录迁移和回滚方案。
- 所有表必须有主键、创建时间、更新时间、必要的唯一索引和状态索引。
- 钱、折扣、时长和数量必须使用明确的整数或定点类型，不能用浮点数。
- 账号密码、验证码、Token 和第三方连接凭据不得明文写入日志或 API 响应。

## 6. 核心业务不变量

以下规则是硬约束，任何实现和重构都不能破坏。

### 6.1 游戏账号

- 同一账号同一时刻只能有一个有效预留或售出记录。
- 创建订单不等于支付成功。
- 支付失败、订单超时和取消必须释放预留。
- 已锁定、已售出、绑定中账号不能被普通库存同步重新标为可售。
- 订单保存商品快照；库存更新不能修改历史订单内容。
- 账号凭据只在授权的已购上下文中展示。

### 6.2 钱包和订单

- 每次余额变化必须有唯一业务号和流水。
- 同一个支付、退款或充值请求重复提交不能重复扣款或入账。
- 订单金额以服务端计算结果为准，前端传入金额只能作为展示信息。
- 会员等级变更不能回算历史订单的等级和折扣快照。
- 订单、库存、权益和退款之间的状态变化必须能追溯。

### 6.3 代练任务

- 一个订单权益不能重复创建多个有效任务，除非业务明确允许次数型权益。
- 一个任务同一时刻只能由一个有效 Worker 持有租约。
- 没有有效租约的 Worker 不能写入进度、成功或失败。
- 完成、失败、取消和退款接口必须幂等。
- Worker 不能直接决定退款金额；退款由订单/售后业务决定。
- 任务日志不能包含账号密码、验证码或完整 Token。

### 6.4 绑定任务

允许的状态必须集中定义，并同步接口、前端文案和测试：

```text
PENDING
PROCESSING
WAIT_INPUT
WAIT_USER
SUCCESS
FAIL
CANCELLED
```

任何新状态必须先更新状态机文档和测试，不得在一个接口中临时增加字符串状态。

## 7. API 和模块边界规则

- 订单模块不能直接访问游戏数据库表。
- 游戏模块不能直接修改钱包余额。
- Worker 不能直接访问商城数据库。
- 前端不能自行推导订单、余额、会员等级、库存或任务状态。
- API 只返回当前调用者有权看到的数据。
- 管理端查看凭据、修改库存、人工退款和重试任务必须有独立权限和审计日志。
- 新接口必须说明认证、幂等键、状态变化、错误码和重试策略。
- 不要为一次性调用创建多层抽象；只有真实存在两个实现或明确的外部替换点时才增加接口。

## 8. 代码修改规则

### 8.1 精准修改

- 只修改当前任务需要的文件。
- 不顺手重构无关代码。
- 不删除现有功能来“简化”代码，除非计划明确要求。
- 不复制 Dujiao-Next 已有的用户、订单、钱包和权限实现。
- 不把游戏业务塞进一个巨型 Service。

### 8.2 先设计再编码

每个阶段开始前必须写清楚：

1. 目标；
2. 当前事实；
3. 数据模型；
4. 状态转换；
5. API 接口；
6. 失败和重试；
7. 测试方式；
8. 不在本阶段做的事情。

如果存在两种合理解释，必须列出两种并暂停，不能默默选择。

### 8.3 测试优先于完成声明

对于状态机、库存锁定、支付、退款、租约和幂等逻辑，必须先写可失败的测试或可重复的集成验证，再实现。

不得用以下证据宣称完成：

- 编译成功但没有业务测试；
- 页面能打开；
- 手工点通一次；
- Mock 返回成功；
- 日志看起来正常。


## 10. 遇到不确定或方向冲突时

必须停止实现并报告：

- 发现的事实；
- 原计划假设；
- 两者的冲突；
- 可能影响的代码和数据；
- 推荐的最小验证。

禁止为了让任务继续而猜测字段、接口、状态、许可证或迁移规则。

## 11. 许可证规则

Dujiao-Next 当前使用 GPL-3.0。必须保留版权和许可证声明。任何对外分发、交付客户或销售修改版前，必须单独检查 GPL 义务和自定义代码的链接/分发方式；这份规则不构成法律意见。

## 12. 完成定义

一个阶段只有同时满足以下条件才算完成：

1. 代码、数据库迁移和接口文档已提交；
2. 正常路径测试通过；
3. 并发、幂等、失败和权限测试通过；
4. 运行日志没有敏感信息；
5. 计划中的验收场景均有结果；
6. 计划和决策记录已更新；
7. 没有把未验证的功能写成“已完成”。

真实数据迁移不是开发阶段的完成条件，必须等所有迁移冻结条件满足后另行执行。
